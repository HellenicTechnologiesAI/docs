This page covers what the team delivers, how to brief a design project correctly, which tools we use, what deliverable formats to expect, and how Creative collaborates with other teams — particularly Web Development.

## Design Process

All Creative Design projects follow this structured process. Account managers and PMs should brief clients on this flow during onboarding to manage expectations around timelines and feedback rounds.

<Steps>
  <Step title="Creative Brief">
    The project starts with a completed creative brief. Use the brief template stored in the shared drive (Creative > Templates > Creative Brief). The brief must capture: project objective, target audience, brand references, mandatory elements, tone of voice, output formats, and deadline. Do not begin any design work without a signed-off brief.
  </Step>
  <Step title="Mood Board & Concept Exploration">
    The designer creates a mood board and explores 2–3 visual directions. This step is shared internally (and sometimes with the client) to align on aesthetic direction before committing to full design.
  </Step>
  <Step title="Initial Design Presentation">
    The designer presents 2–3 distinct concepts to the client. Each concept should differ meaningfully in approach — not just colour variations of the same idea. Concepts are presented in Figma or as PDF exports depending on client preference.
  </Step>
  <Step title="Client Feedback Round 1">
    The client selects a preferred direction and provides structured feedback. Feedback should be collected in writing (email or project management tool) — verbal-only feedback is not accepted as a revision instruction.
  </Step>
  <Step title="Refinements">
    The designer refines the chosen concept based on client feedback. Under the **Design as you GO** model, projects include unlimited revisions — clients can continue iterating until they are satisfied. Ensure the scope of the engagement is confirmed before quoting revision rounds.
  </Step>
  <Step title="Final Delivery">
    Deliver the final assets in all required formats (see Deliverable Formats below). Confirm delivery with the PM and update the project status in the project management tool.
  </Step>
</Steps>

## Deliverable Formats

Deliverables vary by service type. Use this as a reference when briefing clients or confirming final delivery:

| Service | Deliverable Formats |
|---|---|
| Branding | Figma source file, PNG (transparent), SVG, PDF, brand guidelines PDF |
| Web Design | Figma file (with components and assets exported), PNG previews |
| Packaging | AI source file, PDF (print-ready, CMYK, with bleed) |
| Print | INDD source, PDF (print-ready), PDF (digital/screen) |
| Figma to WordPress | Live WordPress site + Figma file (if produced by HT) |

<Note>
  Every new branding project must produce a **brand guidelines document** as a deliverable — no exceptions. Brand guidelines should cover logo usage rules, colour palette (HEX, RGB, CMYK, Pantone where applicable), typography, spacing, and tone of voice. This document protects both the client and our team in future design work.
</Note>

## Collaboration with Web Development

The Creative and Web Development teams work closely on any project that involves both design and build. Follow these protocols to ensure smooth handoffs:

- **Figma files handed to Web Dev must include all assets exported** — icons, images, illustrations, and fonts. Do not hand off a Figma file that relies on external assets the developer has to locate separately.
- **Component naming in Figma must be consistent and logical** — developers use these names when building components.
- **Annotate interactive states** (hover, active, focus, error) in the Figma file. Do not leave developers to guess at interaction design.
- **Confirm responsive breakpoints** are designed and labelled in Figma before handoff (minimum: mobile, tablet, desktop).
- For **Figma to WordPress** projects where the design was provided by the client, the Web Dev lead must review the Figma file for technical feasibility before development begins.

<Tip>
  If you're unsure whether a design is technically implementable as specified, raise it with the Frontend Developer before presenting the design to the client. It's far easier to adjust a Figma file than to rework a live build.
</Tip>
